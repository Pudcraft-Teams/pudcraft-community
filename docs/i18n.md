# Internationalization (i18n)

This project uses [`next-intl`](https://next-intl.dev/) to manage UI copy. The goal: every user-visible string lives in `messages/<locale>.json`, not inlined in components.

The first phase set up the infrastructure (library, locale detection, and the root layout) and migrated a small number of files. The rest of the codebase will be extracted incrementally.

## File layout

```
messages/
  zh.json          # Simplified Chinese (default)
  en.json          # English
src/i18n/
  config.ts        # locales, defaultLocale, cookie name, html lang map
  request.ts       # getRequestConfig — resolves locale per request
```

- `zh` is the default locale; the site is Chinese-first.
- A second locale file MUST mirror the key structure. Values in `messages/en.json` currently **mirror the Chinese source string** (placeholder per team decision — real English translation is deferred). This keeps the UI unbroken if the `en` locale is ever resolved for a user; a blank UI from empty strings is not acceptable. A missing key is also not acceptable.
- Do not rename or rearrange top-level namespaces without updating every file that references them.

## Locale resolution

Per-request in [request.ts](../src/i18n/request.ts):

1. `x-locale` header (if set to `zh` or `en`).
2. `NEXT_LOCALE` cookie (if set to `zh` or `en`).
3. `Accept-Language` header (highest-q supported `zh` / `en` match; ties preserve header order).
4. Falls back to `zh`.

No URL routing yet (no `/en/...` prefix). When we commit to launching English externally, switching to `next-intl`'s path-based routing (`app/[locale]/`) is a follow-up migration — the message files and extraction work carry over unchanged.

## Namespace convention

Top-level keys group by scope, not by file. Nesting goes at most 2 levels deep.

| Namespace | Purpose |
|---|---|
| `metadata` | Site-wide `<title>`, description, keywords |
| `nav` | Header / footer / skip-link |
| `footer` | Footer copy (uses ICU args for year) |
| `errors` | Error page, 404, generic fallbacks |
| `common` | Shared primitives (buttons, empty states, toasts) — add as needed |
| `auth` | Login / register / forgot-password |
| `home` | Homepage-only copy |
| `servers` | Server list, detail, claim, apply, edit, modpack |
| `console` | Owner console |
| `admin` | Admin pages |
| `user` | Profile, settings |
| `notifications` | Notification center |
| `favorites` | Favorites page |
| `changelog` | Changelog |
| `comments` | Comment system |
| `reports` | Report dialog and admin views |

Add a new top-level namespace only when a feature area does not fit any existing one. Keep key names camelCase.

## Using translations

**Server components (default):**

```tsx
import { getTranslations } from "next-intl/server";

export default async function Page() {
  const t = await getTranslations("servers.list");
  return <h1>{t("title")}</h1>;
}
```

**Client components (`"use client"`):**

```tsx
"use client";
import { useTranslations } from "next-intl";

export function FavoriteButton() {
  const t = useTranslations("servers.detail.favorite");
  return <button>{t("add")}</button>;
}
```

**Metadata (via `generateMetadata`):** use `getTranslations` and return the strings inside the `Metadata` object. See [src/app/layout.tsx](../src/app/layout.tsx) for the reference pattern.

**ICU arguments:** put interpolated values in `{}` inside the JSON string, then pass them as the second argument: `t("greeting", { name })`. Use ICU plural / select forms for plurals (`t("count", { n })` with `"{n, plural, one {# item} other {# items}}"`).

## Server-side helpers

For Route Handlers, emails, Zod validation, and other non-component server code:

- **`getRequestLocale(req?)` from `@/i18n/locale`** — resolves the active locale from `x-locale` header → `NEXT_LOCALE` cookie → highest-q supported `Accept-Language` match → `defaultLocale`. Accepts a `Request` arg for Route Handlers; reads `next/headers` when called without args (Server Components, Server Actions).
- **`getZodErrorMap(locale)` from `@/lib/i18nZod`** — pure factory that returns a `ZodErrorMap` mapping Zod issue codes to `errors.validation.*` keys. Usage:
  ```ts
  const locale = await getRequestLocale(req);
  const parsed = schema.safeParse(data, { errorMap: getZodErrorMap(locale) });
  ```
  No global state, no race conditions — each request gets its own map.
- **`apiFetch(url, { locale })` / `buildApiHeaders({ locale, init })` from `@/lib/apiFetch`** — client-side wrappers that inject `x-locale`. Use for new client code; legacy `fetch(...)` call sites fall back to cookie-based locale resolution.

### Email locale

`User.locale` (column added 2026-04-21 via `add_user_locale` migration). Default `"zh"`. Resolution order for outbound mail:

1. Explicit `localeOverride` argument (unauth flows — registration verify, forgot-password — where the recipient isn't logged in).
2. `User.locale` of the recipient (looked up by email).
3. Fall back to `defaultLocale` (`"zh"`).

Email template extraction happens in Batch 7; expect `email.verifyCode`, `email.resetPassword`, `email.claimNotice` namespaces.

### Key parity

Run `pnpm i18n:check` before pushing. The script (`scripts/i18n-check.ts`) walks both `messages/zh.json` and `messages/en.json`, collects all leaf keys, and fails non-zero if the sets disagree. Later CI wiring is a follow-up; meanwhile it's a local pre-push gate.

## What to extract — and what NOT to

Extract:

- Any string rendered to the user in a `.tsx` component (labels, headings, body copy, aria-labels, button text, empty states, toasts, validation messages shown in the UI).
- API response `error` strings that are surfaced unchanged by the client (e.g. form validation messages the UI prints verbatim).
- `<title>`, meta descriptions, Open Graph text.

Do NOT extract:

- `logger.*` messages, thrown `Error` messages, internal debug output.
- Commit messages, doc files, code comments.
- Third-party / upstream content.
- Strings used only by server-to-server communication (worker logs, WebSocket protocol).

When unsure, ask: "does a logged-in user ever see this text?" If yes, extract.

## Adding a string (checklist)

1. Pick the right namespace (see table above).
2. Add the key to **both** `messages/zh.json` and `messages/en.json`. English may be a best-effort draft, but the key must exist.
3. Replace the literal in the component with `t("...")`.
4. Re-run `pnpm tsc --noEmit` to confirm there are no unused imports and the key resolves.

## Testing

- `pnpm lint` and `pnpm tsc --noEmit` catch most issues.
- Manual verification: set a `NEXT_LOCALE=en` cookie in dev, reload, and confirm English renders. Clear the cookie to fall back to Chinese.
- When extracting a string, verify both locales render by flipping the cookie.

## Incremental rollout

The codebase's ~2,400 existing Chinese strings have been migrated:

- **Batch 0** — infrastructure: `getRequestLocale`, `getZodErrorMap`, `apiFetch`, `User.locale` column, `pnpm i18n:check`.
- **Batches 1–7** — complete. ~1,440 keys live in `messages/*.json` across the `auth / servers / comments / favorites / console / admin / user / notifications / reports / changelog / modpacks / email / errors` namespaces.

UI copy, API error responses (`{ error }` and Zod `details.fieldErrors`), and email templates are fully localized. Notifications are rendered in the recipient's locale at creation time (see `src/lib/notification.ts` + `createTranslatedNotification`); historical notification rows retain their original text.

### Server-side translation helpers

- **`flattenZodErrorWithLocale(error, locale)` / `translateZodIssues(issues, locale)`** from `@/lib/i18nZod` — field-specific Zod messages use `errors.validation.<area>.<key>` key paths that are resolved to locale-specific copy at response-serialization time (Zod inline messages bypass `errorMap`, so translation happens here instead).
- **`translateImageValidationError(error, tUploads)`** from `@/lib/i18nImage` — maps `ImageValidationError.code` to `errors.api.uploads.*` copy. `ImageValidationError.message` is developer-facing English and must not be returned to clients.
- **`ModpackError(key, params)`** from `@/lib/modpack` — `parseMrpackFile` / `validateMrpackFile` throw keyed errors resolved via `errors.api.modpacks.*` in `src/app/api/servers/[id]/modpack/route.ts`.
- **`VerifyJobResult.reasonKey`** from `@/lib/queue` — the MOTD verify worker returns a machine-readable key; the API layer maps it to `errors.api.servers.verifyReason*`.

### What intentionally stays Chinese

- `src/lib/moderation.ts` + `src/lib/image-moderation.ts` `LABEL_NAMES`: AI classification labels persisted to moderation logs and shown verbatim in the admin console. Moderators depend on the exact wording.
- `src/components/ServerForm.tsx` + `src/components/HomePageClient.tsx` tag values: stored literally in the DB and used as filter keys.
- `src/lib/serverContent.ts` meta prefixes (e.g. `- 游戏版本：`): serialized into the `Server.content` column as part of the Markdown document.

These are data (not UI copy). Changing them would require a data migration, not a translation.

### What not to do

- Do not re-inline Chinese strings in a file that already calls `useTranslations` / `getTranslations`. Add a key to `messages/*.json` and reference it.
- Do not return `error.message` from custom error classes directly to clients. Either use a machine-readable code / key that the route handler translates, or pass audit metadata (e.g. `error.category`) as `details`.
