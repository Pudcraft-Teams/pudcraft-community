# Internationalization (i18n)

This project uses [`next-intl`](https://next-intl.dev/) to manage UI copy. The goal: every user-visible string lives in `messages/<locale>.json`, not inlined in components.

The first phase set up the infrastructure (library, locale detection, and the root layout) and migrated a small number of files. The rest of the codebase will be extracted incrementally.

## File layout

```
messages/
  zh.json          # Simplified Chinese (default)
  en.json          # English
src/i18n/
  config.ts        # locales, defaultLocale, cookie name, html lang map
  request.ts       # getRequestConfig — resolves locale per request
```

- `zh` is the default locale; the site is Chinese-first.
- A second locale file MUST mirror the key structure. An empty string is acceptable while a translation is pending — a missing key is not.
- Do not rename or rearrange top-level namespaces without updating every file that references them.

## Locale resolution

Per-request in [request.ts](../src/i18n/request.ts):

1. `NEXT_LOCALE` cookie (if set to `zh` or `en`).
2. `Accept-Language` header (first tag starting with `zh` or `en`).
3. Falls back to `zh`.

No URL routing yet (no `/en/...` prefix). When we commit to launching English externally, switching to `next-intl`'s path-based routing (`app/[locale]/`) is a follow-up migration — the message files and extraction work carry over unchanged.

## Namespace convention

Top-level keys group by scope, not by file. Nesting goes at most 2 levels deep.

| Namespace | Purpose |
|---|---|
| `metadata` | Site-wide `<title>`, description, keywords |
| `nav` | Header / footer / skip-link |
| `footer` | Footer copy (uses ICU args for year) |
| `errors` | Error page, 404, generic fallbacks |
| `common` | Shared primitives (buttons, empty states, toasts) — add as needed |
| `auth` | Login / register / forgot-password |
| `home` | Homepage-only copy |
| `servers` | Server list, detail, claim, apply, edit, modpack |
| `console` | Owner console |
| `admin` | Admin pages |
| `user` | Profile, settings |
| `notifications` | Notification center |
| `favorites` | Favorites page |
| `changelog` | Changelog |
| `comments` | Comment system |
| `reports` | Report dialog and admin views |

Add a new top-level namespace only when a feature area does not fit any existing one. Keep key names camelCase.

## Using translations

**Server components (default):**

```tsx
import { getTranslations } from "next-intl/server";

export default async function Page() {
  const t = await getTranslations("servers.list");
  return <h1>{t("title")}</h1>;
}
```

**Client components (`"use client"`):**

```tsx
"use client";
import { useTranslations } from "next-intl";

export function FavoriteButton() {
  const t = useTranslations("servers.detail.favorite");
  return <button>{t("add")}</button>;
}
```

**Metadata (via `generateMetadata`):** use `getTranslations` and return the strings inside the `Metadata` object. See [src/app/layout.tsx](../src/app/layout.tsx) for the reference pattern.

**ICU arguments:** put interpolated values in `{}` inside the JSON string, then pass them as the second argument: `t("greeting", { name })`. Use ICU plural / select forms for plurals (`t("count", { n })` with `"{n, plural, one {# item} other {# items}}"`).

## What to extract — and what NOT to

Extract:

- Any string rendered to the user in a `.tsx` component (labels, headings, body copy, aria-labels, button text, empty states, toasts, validation messages shown in the UI).
- API response `error` strings that are surfaced unchanged by the client (e.g. form validation messages the UI prints verbatim).
- `<title>`, meta descriptions, Open Graph text.

Do NOT extract:

- `logger.*` messages, thrown `Error` messages, internal debug output.
- Commit messages, doc files, code comments.
- Third-party / upstream content.
- Strings used only by server-to-server communication (worker logs, WebSocket protocol).

When unsure, ask: "does a logged-in user ever see this text?" If yes, extract.

## Adding a string (checklist)

1. Pick the right namespace (see table above).
2. Add the key to **both** `messages/zh.json` and `messages/en.json`. English may be a best-effort draft, but the key must exist.
3. Replace the literal in the component with `t("...")`.
4. Re-run `pnpm tsc --noEmit` to confirm there are no unused imports and the key resolves.

## Testing

- `pnpm lint` and `pnpm tsc --noEmit` catch most issues.
- Manual verification: set a `NEXT_LOCALE=en` cookie in dev, reload, and confirm English renders. Clear the cookie to fall back to Chinese.
- When extracting a string, verify both locales render by flipping the cookie.

## Incremental rollout

The codebase has ~2,400 existing Chinese strings across ~180 files. They are being migrated gradually:

- **Shipped:** `metadata`, `nav`, `footer`, root `layout`, `error`, `not-found`.
- **Next batches (by priority):** auth pages → server list / detail → console → admin → everything else.

New PRs that touch a page or component should, at minimum, not introduce new unlocalized strings in files that have already been migrated. Greenfield components should use `useTranslations` / `getTranslations` from day one.
