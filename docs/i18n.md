# 国际化（i18n）

本项目使用 [`next-intl`](https://next-intl.dev/) 管理 UI 文案。目标：所有用户可见字符串都活在 `messages/<locale>.json` 中，**不**内联在组件里。

第一阶段已经完成基础设施搭建（库、locale 检测、根 layout）以及少量文件的迁移。其余代码库会按节奏继续抽取。

## 文件布局

```
messages/
  zh.json          # 简体中文（默认）
  en.json          # 英文
src/i18n/
  config.ts        # locale 列表、默认 locale、cookie 名、html lang 映射
  request.ts       # getRequestConfig —— 按请求解析 locale
```

- 默认 locale 是 `zh`；本站是「中文优先」站点。
- 第二个 locale 文件**必须**镜像键结构。`messages/en.json` 现在的值都是**镜像中文原文**（团队约定的占位 —— 真正的英文翻译延后）。这样即使 `en` locale 真的解析到某个用户身上，UI 也不会空 —— 空 UI 不可接受，缺 key 也不可接受。
- 不要在没同步更新所有引用文件的情况下重命名或重排顶层命名空间。

## Locale 解析

`request.ts`（[`../src/i18n/request.ts`](../src/i18n/request.ts)）按以下顺序解析每次请求的 locale：

1. `x-locale` 请求头（值为 `zh` 或 `en` 时）。
2. `NEXT_LOCALE` cookie（值为 `zh` 或 `en` 时）。
3. `Accept-Language` 请求头（按 q 值取支持的最优 `zh` / `en` 匹配；并列时保留 header 顺序）。
4. 兜底 `zh`。

当前**没有** URL 路由前缀（即 `/en/...`）。等到决定对外上线英文时，再迁到 `next-intl` 的路径前缀路由（`app/[locale]/`），这是后续工作 —— 已抽取的文案文件可以无缝带过去。

## 命名空间约定

顶层 key 按**作用域**分组，不按文件分组。最深嵌套两层。

| 命名空间        | 用途                                                              |
| --------------- | ----------------------------------------------------------------- |
| `metadata`      | 全站 `<title>`、description、keywords                             |
| `nav`           | 顶栏 / 页脚 / skip-link                                           |
| `footer`        | 页脚文案（用 ICU 参数注入年份）                                   |
| `errors`        | 错误页、404、通用兜底                                             |
| `common`        | 共用原语（按钮、空状态、Toast）—— 按需添加                        |
| `auth`          | Misskey MiAuth 登录入口页（**唯一**登录入口）                     |
| `home`          | 仅首页文案                                                        |
| `servers`       | 服务器列表、详情、认证、申请、编辑、整合包                        |
| `console`       | 服主控制台                                                        |
| `admin`         | 管理后台                                                          |
| `user`          | 用户主页、设置                                                    |
| `notifications` | 通知中心                                                          |
| `favorites`     | 收藏页                                                            |
| `changelog`     | 更新日志                                                          |
| `comments`      | 评论系统                                                          |
| `reports`       | 举报弹窗与管理员视图                                              |

只有当一个功能区域确实在以上命名空间里都放不下时，才新增顶层命名空间。Key 名用 camelCase。

## 使用翻译

**Server Component（默认）：**

```tsx
import { getTranslations } from "next-intl/server";

export default async function Page() {
  const t = await getTranslations("servers.list");
  return <h1>{t("title")}</h1>;
}
```

**Client Component（`"use client"`）：**

```tsx
"use client";
import { useTranslations } from "next-intl";

export function FavoriteButton() {
  const t = useTranslations("servers.detail.favorite");
  return <button>{t("add")}</button>;
}
```

**Metadata（通过 `generateMetadata`）**：使用 `getTranslations`，把字符串放进返回的 `Metadata` 对象。参考写法见 [src/app/layout.tsx](../src/app/layout.tsx)。

**ICU 参数**：在 JSON 字符串里用 `{}` 包住要插值的 key，再作为 `t()` 第二个参数传入：`t("greeting", { name })`。复数走 ICU plural / select 形式（`t("count", { n })` 配 `"{n, plural, one {# item} other {# items}}"`）。

## 服务端辅助函数

Route Handler、Zod 校验等非组件的服务端代码：

- **`@/i18n/locale` 中的 `getRequestLocale(req?)`** —— 按 `x-locale` 请求头 → `NEXT_LOCALE` cookie → 按 q 值匹配的 `Accept-Language` → `defaultLocale` 顺序解析当前 locale。Route Handler 可以传入 `Request`；不传参数时（Server Component / Server Action）从 `next/headers` 读。
- **`@/lib/i18nZod` 中的 `getZodErrorMap(locale)`** —— 纯工厂函数，返回一个 `ZodErrorMap`，把 Zod issue code 映射到 `errors.validation.*` key。用法：
  ```ts
  const locale = await getRequestLocale(req);
  const parsed = schema.safeParse(data, { errorMap: getZodErrorMap(locale) });
  ```
  没有全局状态、没有竞争 —— 每次请求都是自己的一份 map。
- **`@/lib/apiFetch` 中的 `apiFetch(url, { locale })` / `buildApiHeaders({ locale, init })`** —— 客户端封装，会自动注入 `x-locale`。新写客户端代码请用它；遗留的 `fetch(...)` 调用点回退到基于 cookie 的 locale 解析。

### 用户 locale

`User.locale` 列于 2026-04-21 通过 `add_user_locale` 迁移引入。默认 `"zh"`。随着邮箱与整套 SMTP 管线在 Misskey MiAuth 迁移中被移除，`User.locale` 现在**只**用于服务端渲染页面的语种选择 —— 不再有出站邮件。

### Key 平价检查

push 之前先跑 `pnpm i18n:check`。脚本（`scripts/i18n-check.ts`）会同时遍历 `messages/zh.json` 与 `messages/en.json`，收集所有叶子 key，集合不一致就以非零退出码失败。CI 集成是后续工作；当前先作为本地 pre-push 闸门。

## 抽什么、不抽什么

**要抽**：

- `.tsx` 组件中渲染给用户看到的所有字符串（label、标题、正文、aria-label、按钮文案、空状态、Toast、UI 上展示的校验信息）。
- API 响应里 `error` 字段中**会被客户端原样展示**的文案（例如 UI 直接打印的表单校验提示）。
- `<title>`、meta description、Open Graph 文案。

**不要抽**：

- `logger.*`、`throw new Error(...)`、内部调试输出。
- Commit message、文档文件、代码注释。
- 第三方 / 上游内容。
- 仅服务端到服务端通信使用的字符串（worker 日志、WebSocket 协议字段）。

不确定时问：「登录用户会在某处看到这段文字吗？」答案是肯定 → 抽。

## 新增字符串清单

1. 选合适的命名空间（参考上表）。
2. **同时**给 `messages/zh.json` 与 `messages/en.json` 添加 key。英文可以是尽力而为的草稿，但 key 必须存在。
3. 把组件里的字面量替换为 `t("...")`。
4. 重新跑 `pnpm tsc --noEmit`，确认没有未使用 import 且 key 能解析。

## 测试

- `pnpm lint` 与 `pnpm tsc --noEmit` 能抓到大部分问题。
- 手动验证：在开发环境设置 `NEXT_LOCALE=en` cookie，刷新，确认英文渲染。清掉 cookie 应回到中文。
- 抽完字符串后，切换 cookie 在两种 locale 各跑一遍。

## 渐进式推进

代码库原有约 2,400 条中文字符串已迁移：

- **Batch 0** —— 基础设施：`getRequestLocale`、`getZodErrorMap`、`apiFetch`、`User.locale` 列、`pnpm i18n:check`。
- **Batches 1–7** —— 完成。约 1,390 个 key 分散在 `auth / servers / comments / favorites / console / admin / user / notifications / reports / changelog / modpacks / errors` 命名空间。

UI 文案与 API 错误响应（`{ error }` 与 Zod `details.fieldErrors`）已完全本地化。通知在创建时按收件人 locale 渲染（见 `src/lib/notification.ts` + `createTranslatedNotification`）；历史通知行保留原始文本。

### 服务端翻译辅助函数

- **`@/lib/i18nZod` 中的 `flattenZodErrorWithLocale(error, locale)` / `translateZodIssues(issues, locale)`** —— 字段级 Zod 文案使用 `errors.validation.<area>.<key>` 路径，在响应序列化阶段解析为目标 locale（Zod 的内联 message 会绕过 `errorMap`，所以翻译动作落在这里）。
- **`@/lib/i18nImage` 中的 `translateImageValidationError(error, tUploads)`** —— 把 `ImageValidationError.code` 映射到 `errors.api.uploads.*` 文案。`ImageValidationError.message` 是面向开发者的英文文案，**不能**直接返回给客户端。
- **`@/lib/modpack` 中的 `ModpackError(key, params)`** —— `parseMrpackFile` / `validateMrpackFile` 抛出带 key 的错误，由 `src/app/api/servers/[id]/modpack/route.ts` 通过 `errors.api.modpacks.*` 翻译成目标语种。
- **`@/lib/queue` 中的 `VerifyJobResult.reasonKey`** —— Worker 返回机器可读 key，由 API 层映射到 `errors.api.servers.verifyReason*`。

### 故意保持中文的内容

- `src/lib/moderation.ts` + `src/lib/image-moderation.ts` 中的 `LABEL_NAMES`：AI 分类标签会持久化到审核日志，并在管理后台原文展示。审核员依赖固定措辞。
- `src/components/ServerForm.tsx` + `src/components/HomePageClient.tsx` 中的 tag 值：以字面量形式入库，并被作为筛选 key 使用。
- `src/lib/serverContent.ts` 中的 meta 前缀（如 `- 游戏版本：`）：序列化进 `Server.content` 列里 Markdown 文档的一部分。

这些都是**数据**（不是 UI 文案）。要修改它们需要做数据迁移，而不是翻译。

### 不要做的事

- 已经在用 `useTranslations` / `getTranslations` 的文件，**不要**再内联中文字符串。给 `messages/*.json` 加 key 再引用。
- **不要**把自定义错误类的 `error.message` 直接返回给客户端。要么使用机器可读的 code / key，由 route handler 翻译；要么把审计元数据（例如 `error.category`）作为 `details` 传出。
